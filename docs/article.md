## Главные выводы из основной PDF, релевантные обеим веткам

Статья описывает динамическую компрессию поверх нескольких существующих методов и сравнивает static/dynamic finite-grid behavior как на logistic-regression задаче, так и на ResNet-задаче.

Ключевое отображение алгоритмов:
- `EF21` использует **biased** ветку, то есть `DB`
- `DIANA` использует **unbiased** ветку, то есть `DU`
- `DASHA` использует **unbiased** ветку, то есть `DU`

Также статья использует совместимость finite-grid rounding со sparsification family:
- `Top-k`
- `Rand-k`

Dynamic data type в статье описывается как обновляемая сетка/тип данных по некоторому trigger rule:
- norm/message-size based trigger;
- либо fixed-iteration trigger.

Для практической реализации в этом проекте это означает:
- dynamic rule должен быть явным;
- он должен быть залогирован;
- static/dynamic должны быть сравнимы при одинаковом communication budget.

# Часть I. Small-datasets / logistic regression

## Что берем как рабочую постановку

Для этой ветки нужно ориентироваться на:
- LibSVM-style датасеты;
- `mushrooms`, `a9a`, `w8a`;
- разбиение на `n = 10` клиентов;
- logistic regression oriented objective;
- общение и сравнение методов по оси `kbits / n`.

## Что пользователь потребовал поверх статьи

Пользователь явно уточнил:
- обязательные датасеты: `mushrooms`, `a9a`, `w8a`;
- все кривые внутри одной графической семьи должны заканчиваться на одном `Ox = kbits / n`;
- лишние вычисления выполнять нельзя;
- нужна композиция `gradient -> DB(4-bit) -> TopK(10%)`;
- в static/dynamic части нужно сохранить `p=2`, `p=4` и добавить `p=8`;
- ветка должна быть оптимизирована под **MacBook Pro M4 Pro**.

## Что найдено в коде и что из этого следует

В `bits_complexity_paper-main.zip` уже есть:
- `EF21`
- `Diana`
- часть finite-grid / dynamic machinery
- `Topk`, `RandK`
- часть small-dataset setup

Но отсутствуют или недостаточно четко оформлены:
- `w8a`
- точный bit accounting
- удобная композиция компрессоров
- единый cutoff controller
- удобный runner / CSV contract

## Конфликты для ветки small-datasets

### Конфликт A1 — статья/цель vs текущий архив
Требуемый набор датасетов включает `w8a`, но в архиве этот путь отсутствует или не доведен.

### Конфликт A2 — качество оси Ox
Текущий архив использует недостаточно строгий bit accounting для publication-quality сравнения по `kbits / n`.

### Конфликт A3 — dynamic rule
Текущий код содержит dynamic helpers, но их поведение нужно отдельно проверить и зафиксировать явно, а не оставлять как неявную эвристику.

## Что считать входом для реализации ветки small-datasets
- исходный small-datasets код
- пользовательские требования из чата
- mapping методов из основной статьи
- `docs/codex_tasks_small_datasets.md`
- `docs/planned_graphs_small_datasets.md`

## Что считать выходом для реализации ветки small-datasets
- runnable code
- одна точка входа для экспериментов
- CSV-логи
- графики family A / family B
- краткие инструкции запуска

# Часть II. CIFAR-10 / ResNet18

## Что берем как рабочую постановку

Для второй ветки фиксируем:
- `CIFAR-10`
- `ResNet18`
- `10` клиентов
- homogeneous split
- comparison by communication budget, а не только by round count
- обязательные CSV-логи уровней `round`, `epoch`, `batch`
- целевая машина: **A100 40GB / 80GB**
- требование: **минимально загружать CPU**

## Что пользователь потребовал поверх статьи

Пользователь зафиксировал:
- нужно форкнуть/переосмыслить `FedAvg` под compression-FL;
- нужны `EF21`, `DIANA`, `DASHA`;
- нужны baseline-компрессоры `Top-k`, `Rand-k`;
- нужны прогоны по `16 / 32 / 64` битам для unbiased ветки;
- EF21 должен идти отдельной biased веткой;
- нужен сбор данных по `round / epoch / batch`;
- важен одинаковый итоговый communication budget на клиента, а не только число раундов.

## Что найдено в `PPBC-rare_participation.zip`

Архив содержит полезную инфраструктуру, но не готовую реализацию нужной постановки.

Наблюдения по аудиту:
- есть `FedAvg`-подобный базовый каркас;
- есть `ResNet18` и CIFAR-конфиги;
- есть `torch.multiprocessing` / `Pipe`-ориентированная логика;
- текущая логика апдейта ближе к model delta, а не к paper-style compressed gradient state;
- конфиги и исполнение ориентированы скорее на round-driven сценарий, чем на communication-budget-driven.

## Конфликты для ветки CIFAR

### Конфликт B1 — update semantics
Текущий archive update flow не совпадает один-в-один с paper-level абстракцией EF21/DIANA/DASHA.

### Конфликт B2 — системный дизайн
Текущий multiprocessing / Pipe дизайн плохо сочетается с требованием пользователя минимизировать CPU utilization на A100.

### Конфликт B3 — control variable
Текущий код думает в раундах, а пользователь хочет сопоставление по transmitted `kbit / client`.

## Что считать входом для реализации ветки CIFAR
- `PPBC-rare_participation.zip`
- пользовательские требования
- method mapping из основной статьи
- `codex_tasks_cifar_resnet.md`
- `planned_graphs_cifar_resnet.md`

## Что считать выходом для реализации ветки CIFAR
- новая clean compression-FL ветка
- single-process / single-GPU-first path
- `EF21`, `DIANA`, `DASHA`, `Top-k`, `Rand-k`
- точный учет бит
- equal-budget stopping
- round/epoch/batch CSV logs
- plotting scripts и графики

# Часть III. Внешние статьи, которые использовать только по назначению

Основное правило проекта:
- общая постановка и связь методов берется из основной PDF;
- точные детали отдельных алгоритмов — из их оригинальных статей;
- пользовательские требования могут переопределять экспериментальный набор.

Какие внешние paper-level источники нужны:
- `EF21` — для точной алгоритмической формулировки biased memory-based method;
- `DIANA` — для точной unbiased formulation;
- `DASHA` — для точной unbiased formulation;
- `Top-k` и `Rand-k` — для baseline semantics и корректного разграничения biased/unbiased.

## Обязательный вход
Для любой из двух веток Codex должен всегда читать минимум:

Для любой из двух веток на выходе должны быть:
- измененный код;
- способ воспроизводимого запуска;
- CSV-логи для всех обязательных графиков;
- скрипты построения графиков;
- минимальные инструкции запуска;
- явная фиксация конфликтов, если постановка пользователя расходится со старым кодом или статьей.
